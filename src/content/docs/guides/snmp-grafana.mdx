## Concepts

### What is Monitoring / Network Monitoring?

Network monitoring is the process of continuously observing network devices, services, and traffic to understand their availability, health, and performance.

A network administrator might want to know:

* Is a device online?
* Are its network interfaces up?
* How much network traffic is it handling?
* Is it experiencing errors or dropped packets?
* How much CPU, memory, or storage is it using?
* Has any of this changed over time?

### Why monitor?

Without monitoring, administrators may not know something is wrong until a user reports it.

Monitoring allows administrators to:

* Detect problems earlier
* Identify unusual behavior
* Compare current performance against normal performance
* Track changes over time
* Make decisions about capacity and upgrades

<Aside title="Network+ term: Baseline" type="tip">
A baseline represents the normal performance of a network or device. Current measurements can be compared against the baseline to identify unusual behavior.
</Aside>

## SNMP

### What is SNMP?

**SNMP** stands for ***Simple Network Management Protocol***.

It is an application-layer protocol used to monitor and manage network-connected devices, and can be supported by many different types of equipment.

<Aside title="Network+ Port Numbers" type="tip">
The default ports to know for SNMP are:
- UDP 161 — SNMP queries
- UDP 162 — SNMP notifications/traps
</Aside>

<Aside title="SNMPv3" type="note">
SNMPv3 introduces enhanced security features compared to SNMPv1 and SNMPv2c, including authentication and encryption. For the purposes of this guide, we will focus on SNMPv2c, which is simpler to configure and sufficient for our locally restricted monitoring environment. In a production environment where SNMP traffic travels across a network, SNMPv3 is generally preferred.
</Aside>

#### SNMP Agent

Software running on the device being monitored.

The agent:

* Collects information about the device
* Makes that information available through SNMP
* Responds to requests from an SNMP manager

On our Raspberry Pi, we'll use `snmpd`.

#### SNMP Manager

The SNMP manager is the system that queries and collects information from SNMP agents.

It is responsible for:

* Sending requests to SNMP agents
* Receiving responses from SNMP agents
* Processing the returned management information

SNMP managers are commonly part of network management and monitoring systems. In this project, we will eventually use Telegraf to automatically poll our SNMP agent and collect its metrics.

For this guide, we will start by using SNMP tools such as `snmpwalk` and `snmpget` to manually query our Raspberry Pi, and then move to using Telegraf as our SNMP manager in combination with InfluxDB and Grafana to collect and visualize data from our Raspberry Pi devices.

### Package Installation

We will need the following packages to get started with SNMP:

* `snmp`: Command-line tools (like snmpwalk, snmpget) used to query SNMP agents
* `snmpd`: The SNMP agent daemon that runs on a background service to report stats from your machine
* `snmp-mibs-downloader`: Installs standard, text-readable MIB files so you can query system metrics by name instead of numeric OID. This is particularly useful when using tools like `snmpwalk` and `snmpget` to make the output more human-readable.

```bash title="Installing SNMP Packages"
sudo apt install snmp snmpd snmp-mibs-downloader
```

### Object Identifiers (OIDs)

SNMP needs a standardized way to identify every piece of information that can be requested.

It uses an ***Object Identifier***, or **OID**. 

An OID is a globally unique identifier that represents a specific piece of information in the SNMP-managed device.

OIDs are organized in a ***hierarchical tree structure***, and each node in the tree has a numeric identifier. By querying an OID, you can retrieve the corresponding value from the device. For example, `.1.3.6.1.2.1.1.5.0` is the OID for the system name of the device.

```text
1 - iso
└── .3 - org
    └── .6 - dod
        └── .1 - internet
            └── .2 - mgmt
                └── .1 - mib-2
                    ├── .1 - system
                    │   ├── .1 - sysDescr
                    │   ├── .3 - sysUpTime
                    │   └── .5 - sysName
                    └── .2 - interfaces
```

*Thats a lot of numbers*, so here is where MIBs come in.

### Management Information Bases (MIBs)

A Management Information Base (MIB) defines and describes objects that can be managed through SNMP. MIBs give meaningful names to OIDs.

Instead of remembering:

```text
.1.3.6.1.2.1.1.5.0
```

we can use:

```text
SNMPv2-MIB::sysName.0
```

### snmpd

#### Default Configuration

The following is an example of the default configuration for snmpd (minus all the comments).

```bash title="/etc/snmp/snmpd.conf"
itclub@monk:~ $ sudo grep -vE '^\s*(#|$)' /etc/snmp/snmpd.conf
sysLocation    Sitting on the Dock of the Bay
sysContact     Me <me@example.org>
sysServices    72
master  agentx
agentaddress  127.0.0.1,[::1]
view   systemonly  included   .1.3.6.1.2.1.1
view   systemonly  included   .1.3.6.1.2.1.25.1
rocommunity  public default -V systemonly
rocommunity6 public default -V systemonly
rouser authPrivUser authpriv -V systemonly
includeDir /etc/snmp/snmpd.conf.d
itclub@monk:~ $ 
```

Some configuration options in the default snmpd.conf include:
* `agentaddress  127.0.0.1,[::1]` - specifies the IP addresses and ports on which the SNMP agent listens for incoming requests. As mentioned earlier, for the purposes of this guide, local is sufficient.
* `view systemonly included <OID>` - defines a view named `systemonly` that includes the specified OID subtree, allowing access to only the objects within that subtree.
* `rocommunity public default -V systemonly` - defines a read-only community string `public` that has access to the `systemonly` view. This allows SNMP clients to query system-related information. A community string acts somewhat like a shared access string in SNMPv1/v2c, however it is sent without encryption. For SNMPv3, instead of a community string, you need to provide (with the `rouser` option) a username, password, and optionally an encryption key for secure communication, which is why we aren't using SNMPv3 in this guide.

#### snmpget

snmpget is used to retrieve individual management values using SNMP GET requests. It allows you to query specific OIDs or MIB names to get their current values.

```bash title="snmpget Example"
snmpget -v2c -c public localhost SNMPv2-MIB::sysName.0
```

Options used in the example:
- `-v2c` specifies the SNMP version to use (in this case, SNMPv2c)
- `-c public` specifies the community string (in this case, `public`)
- `localhost` specifies the target host (in this case, the local machine)
- `SNMPv2-MIB::sysName.0` specifies the OID (or MIB name) to query (in this case, the system name)

Your output should show the system name of the local machine, which in this case is `monk`:

```bash title="snmpget Output Example"
itclub@monk:~ $ snmpget -v2c -c public localhost SNMPv2-MIB::sysName.0
SNMPv2-MIB::sysName.0 = STRING: monk
```

<Aside title="Demonstrating what snmp-mibs-downloader does" type="tip">

```bash title="Without MIBs"
itclub@monk:~ $ snmpget -v2c -c public localhost .1.3.6.1.2.1.1.5.0
iso.3.6.1.2.1.1.5.0 = STRING: "monk"
```

versus

```bash title="With MIBs"
itclub@monk:~ $ snmpget -v2c -c public localhost SNMPv2-MIB::sysName.0
SNMPv2-MIB::sysName.0 = STRING: monk
```

</Aside>

#### snmpwalk

snmpwalk is used to retrieve a subtree of management values using SNMP GETNEXT requests. It allows you to query a range of OIDs or MIB names to get all the current values within that subtree.

```bash title="snmpwalk Example"
snmpwalk -v2c -c public localhost IF-MIB::ifDescr
```

See [snmpget](#snmpget) for a description of the options used.

Your output should show the descriptions of all network interfaces on the local machine:

```bash title="snmpwalk Output Example"
itclub@monk:~ $ snmpwalk -v2c -c public localhost IF-MIB::ifDescr
IF-MIB::ifDescr.1 = STRING: lo
IF-MIB::ifDescr.2 = STRING: eth0
IF-MIB::ifDescr.3 = STRING: wlan0
itclub@monk:~ $ 
```

### Tables and Indexes

SNMP commonly represents information about multiple similar objects using ***tables***.
Each row in a table is uniquely identified by an ***index***, which allows you to correlate and retrieve specific information about that row across different columns in the SNMP table.

So for example, when looking at the `IF-MIB::ifDescr` table, each network interface is associated with a unique index.

```bash title="Indices of Network Interfaces"
itclub@monk:~ $ snmpwalk -v2c -c public localhost IF-MIB::ifDescr
IF-MIB::ifDescr.1 = STRING: lo
IF-MIB::ifDescr.2 = STRING: eth0
IF-MIB::ifDescr.3 = STRING: wlan0
```

```bash title="Network Interface Statuses"
itclub@monk:~ $ snmpwalk -v2c -c public localhost IF-MIB::ifOperStatus
IF-MIB::ifOperStatus.1 = INTEGER: up(1)
IF-MIB::ifOperStatus.2 = INTEGER: up(1)
IF-MIB::ifOperStatus.3 = INTEGER: down(2)
```

From these two commands, we can see that the network interface `eth0` is associated with the index `2`, and thus has a status of `up(1)`.

<Aside title="Counters vs Rates" type="caution">
SNMP provides counters for various metrics, such as bytes transmitted or received. These counters continuously increase over time. To understand the actual rate of change (e.g., network throughput), you need to calculate the difference between successive counter values over a specific time interval.

So for example if two successive SNMP counter readings are taken 10 seconds apart:

12:00:00  RX = 100,000,000 bytes \
12:00:10  RX = 105,000,000 bytes

5,000,000 bytes transferred in 10 seconds \
= 500,000 bytes/second \
= 4,000,000 bits/second \
= 4 Mbps
</Aside>

<Aside title="SNMP Data Types" type="note">
You may notice types such as INTEGER, Gauge32, Counter32, and Counter64 in SNMP output.
- INTEGER — a numeric value, sometimes representing an enumerated state such as up(1).
- Gauge32 — a value that can increase or decrease, such as interface speed.
- Counter32 / Counter64 — counters that generally increase as events occur, such as bytes received or packets discarded.
- STRING — text, such as an interface or system name.
</Aside>

### The Problem With What We're Doing

Manually retrieving system information using SNMP commands like `snmpget` and `snmpwalk` is not scalable. For a single device, and for looking at the system's status at a specific point in time, it might be feasible. However, this approach quickly becomes cumbersome as the number of devices increases or when continuous monitoring is required.

We need something to:
* Query SNMP automatically
* Query it repeatedly at regular intervals over time
* Store the collected data
* Calculate changes over time
* Visualize the results

This is where automated monitoring solutions like Telegraf, InfluxDB, and Grafana come into play, allowing for continuous data collection, storage, and visualization across multiple devices.

To run Telegraf, InfluxDB, and Grafana in a consistent and isolated environment, we can use Docker. Docker allows us to containerize these applications, making it easier to deploy and manage them without worrying about dependencies and system configurations.

See our [portainer](/guides/portainer/) guide for a more comprehensive explanation of Docker and container management.

    ##### System Uptime
    ```text title="System Uptime"
    from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "snmp")
    |> filter(fn: (r) => r._field == "uptime")
    |> last()
    |> map(fn: (r) => ({ r with _value: float(v: r._value) / 100.0 }))
    ```

    ##### CPU Utilization
    `hrProcessorLoad` (and consequently the `cpu` and `load_percent` data we are importing to InfluxDB) reports utilization separately for each logical processor. This query retrieves the latest reading for each processor and calculates their mean to produce an overall CPU utilization percentage.

    ```text title="Current CPU Utilization"
    from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "cpu")
    |> filter(fn: (r) => r._field == "load_percent")
    |> last()
    |> group()
    |> mean()
    ```

    ##### Memory Utilization
    Linux uses otherwise-unused memory for caching, so the amount of memory marked as “used” does not necessarily represent memory pressure. Instead, we'll calculate utilization using available memory:
    
    **Memory Utilization = (1 − Available Memory / Total Physical Memory) × 100**

    ```text title="Memory Utilization"
    total = from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "storage")
    |> filter(fn: (r) => r.storage == "Physical memory")
    |> filter(fn: (r) => r._field == "size")
    |> last()
    |> findRecord(fn: (key) => true, idx: 0)

    available = from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "storage")
    |> filter(fn: (r) => r.storage == "Available memory")
    |> filter(fn: (r) => r._field == "size")
    |> last()
    |> findRecord(fn: (key) => true, idx: 0)

    from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "storage")
    |> filter(fn: (r) => r.storage == "Physical memory")
    |> filter(fn: (r) => r._field == "size")
    |> last()
    |> map(fn: (r) => ({
        r with
        _value: (1.0 - (float(v: available._value) / float(v: total._value))) * 100.0
    }))
    ```

    ##### Disk Utilization
    **Disk Utilization = Used Space / Total Space × 100**

    ```text title="Disk Utilization"
    size = from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "storage")
    |> filter(fn: (r) => r.storage == "/")
    |> filter(fn: (r) => r._field == "size")
    |> last()
    |> findRecord(fn: (key) => true, idx: 0)

    from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "storage")
    |> filter(fn: (r) => r.storage == "/")
    |> filter(fn: (r) => r._field == "used")
    |> last()
    |> map(fn: (r) => ({
        r with
        _value: float(v: r._value) / float(v: size._value) * 100.0
    }))
    ```

    ##### Network Traffic
    Earlier, we calculated a traffic rate by finding the difference between two SNMP counter readings over time. The derivative() function performs that calculation automatically. Because ifHCInOctets and ifHCOutOctets count bytes, multiplying the resulting bytes-per-second value by 8 converts it to bits per second.

    <Tabs>
    <TabItem label="Query A">
    ```text title="eth0 Inbound Traffic"
    from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "interface")
    |> filter(fn: (r) => r.interface == "eth0")
    |> filter(fn: (r) => r._field == "in_octets")
    |> derivative(unit: 1s, nonNegative: true)
    |> map(fn: (r) => ({
        r with
        _value: float(v: r._value) * 8.0
    }))
    |> set(key: "_field", value: "Inbound")
    |> keep(columns: ["_time", "_value", "_field"])
    ```
    </TabItem>
    <TabItem label="Query B">
    ```text title="eth0 Outbound Traffic"
    from(bucket: "network")
    |> range(start: v.timeRangeStart, stop: v.timeRangeStop)
    |> filter(fn: (r) => r._measurement == "interface")
    |> filter(fn: (r) => r.interface == "eth0")
    |> filter(fn: (r) => r._field == "out_octets")
    |> derivative(unit: 1s, nonNegative: true)
    |> map(fn: (r) => ({
        r with
        _value: float(v: r._value) * 8.0
    }))
    |> set(key: "_field", value: "Outbound")
    |> keep(columns: ["_time", "_value", "_field"])
    ```
    </TabItem>
